# RPI_Cluster

Single-entry-point **Regulatory & Policy Intelligence** scraper for pharma competitor
tracking across the Andean + CARICAM region, plus EMA and FDA as forecast references.
It extracts competitor product **approvals** and **submissions** from 9 health
authorities, normalizes everything into one canonical 19-field schema, writes
per-country CSVs, consolidates them into a master file, and builds an xlsx
executive-summary report.

**This pipeline is local-only by design.** Extracted data never leaves the machine:
there is no Notion/Airtable push and no email delivery. Company compliance does not
permit automated connectors, so results are handed over by opening the generated
workbook and copying into the team's consolidated file.

## Quick start

```bash
python -m venv .venv && .venv\Scripts\Activate.ps1   # Windows
pip install -r requirements.txt
python -m unittest discover -s tests -t .            # verify the install (132 tests)
python rpi_cluster.py
```

That last command runs the full pipeline. Output lands in `./output`.

> **Handing this to a non-developer?** Two Spanish guides assume no programming background:
> - **[INSTALACION.md](INSTALACION.md)** — install Python/venv, first run, common errors.
> - **[RUNBOOK.md](RUNBOOK.md)** — day-to-day operation: cadence, the 5 pre-report checks,
>   per-country failure playbook, each source's real limits, data red flags, and escalation.
>
> Both stress the `Empty` vs `Failed` distinction: `Empty` is a valid finding ("we searched,
> there is no registration"), `Failed` means nothing is known. Reporting a `Failed` as "no
> competitor product" is the costliest mistake possible with this tool.

Configuration is optional — `.env` carries no credentials (just an output path and the
free OpenFDA key). It is still gitignored so nothing machine-specific gets committed.

### Options

| Flag | Purpose |
|------|---------|
| `--output-dir PATH` | Local folder for CSV output (default `./output` or `$RPI_OUTPUT_DIR`) |
| `--country CODE` | Run only one country: `PE CO SV GT HN DO CR EC EMA FDA` |
| `--molecule INN` | Run only one molecule instead of the full list |
| `--no-selenium` | Skip Selenium-dependent countries (prints a warning, marks them 🔄) |
| `--tier-a` | Run only the reliable HTTP sources (EMA, FDA, Colombia, El Salvador, Honduras) — the unattended/scheduled preset |
| `--no-ec` | Exclude Ecuador from a full run (it runs by default; its bulk report adds ~25-45s). Tier-A never includes Ecuador. |
| `--no-report` | Skip generating the xlsx executive-summary report |
| `--fda-api-key KEY` | OpenFDA API key (raises the rate limit 240 → 1000 req/min) |
| `--headless` | Run browsers headless |
| `--non-interactive` | Never pause for manual input |

`.env` is optional and holds no credentials — only an output path and the free
OpenFDA rate-limit key. See `.env.example`.

## Scheduled automation (the unattended slice)

Only the HTTP sources can run fully unattended (no browser, no CAPTCHA, no human).
The `--tier-a` preset runs exactly those — EMA, FDA, Colombia approvals, El Salvador,
Honduras — then normalizes, consolidates and builds the **xlsx executive-summary
report** (`RPI_REPORT_DDMMYYYY.xlsx`: KPIs, molecule×country matrix, last-90-day
competitor approvals, full data):

```bash
python rpi_cluster.py --tier-a
```

- **Report** is generated by default (disable with `--no-report`).
- **Distribution is manual and deliberate:** the report and CSVs stay on disk. Whoever
  runs it opens the workbook and copies the rows into the team's consolidated file.
  There is no automated delivery of any kind.

**Windows scheduling** (this is a local project, so use Task Scheduler, not a cloud
routine): `scripts\run_tier_a.ps1` is the wrapper, and `scripts\register_task.ps1`
registers it:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\register_task.ps1
# default: daily 07:00 — edit $Time/$Schedule in the script to change
# run now: schtasks /Run /TN RPI_TierA   |   remove: schtasks /Delete /TN RPI_TierA /F
```

**Peru — DISABLED, out of scope (16/08/2026).** DIGEMID sits behind a Cloudflare **managed
challenge** ("Just a moment…", no widget to solve). Clearing it requires a SeleniumBase
**UC-mode** (undetected) browser — technically it worked, but driving a stealth driver past a
government portal's bot protection is a compliance question the company has not signed off on.
Both Peru extractors are therefore marked `disabled` in the registry: a run reports them as
⛔ Disabled with the reason and continues normally, and no Peru CSV is written.

Nothing was deleted. `extractors/pe_approvals.py`, `pe_submissions.py`, the `--pe-stealth`
flag and their tests are all intact, and previously collected Peru data was moved to
`output/_quarantine/`. **To re-enable once Legal/IT rule on it:** delete the two `"disabled"`
keys from the `pe_approvals` / `pe_submissions` entries in `EXTRACTORS`, then
`pip install seleniumbase` and run `python rpi_cluster.py --country PE --pe-stealth`.
Note this needs local Chrome + a display (headful) — it never fits a cloud routine; a
web-unlocker API would be the only path there.

The merge-don't-clobber logic means the scheduled Tier-A refresh never wipes data you
collect from the browser portals.

## Execution order

API-first, Selenium-last for efficiency:

1. EMA · 2. FDA · 3. Colombia approvals — *requests, fast*
4. Honduras · 5. El Salvador · 6. Guatemala · 7. Dominican Rep · 8. Costa Rica
   · 9. Peru approvals ⛔ · 10. Peru submissions ⛔ · 11. Colombia submissions ⛔ — *disabled*
12. Ecuador — *requests + CSV, rate-limited 15–22 s/request*
13. Consolidate

Each country is wrapped in try/except — a failure is logged and the run continues.

## Layout

```
rpi_cluster.py          Entry point / orchestrator
config.py               Molecule list, country metadata, source URLs, HTTP session
normalize.py            Canonical normalization (status map, date parse, dedup, PK rule)
consolidate.py          Merge per-country CSVs → master file
extractors/             One module per source (+ selenium_base.py shared helpers)
report.py               xlsx executive-summary builder (local file, no delivery)
output/                 CSV output + xlsx report + run log + unmapped_status.log
```

## Canonical schema (19 fields, fixed order)

`registration_number, country_code, health_authority, record_type, product_name,
api, concentration, dosage_form, applicant, manufacturer, manufacturer_country,
status, process_type, submission_date, approval_date, expiration_date,
molecule_search_term, source_url, extraction_date`

- `registration_number` is the primary key — rows without it are dropped.
- Dates are `DD/MM/YYYY`. `api` / `molecule_search_term` are uppercase.
- Empty values are blank cells (never `N/A` / `-` / `ND`).
- CSVs are UTF-8 with BOM (`utf-8-sig`) for Excel.

## Operational notes

- **Selenium selectors:** the LATAM portals are scraped with defensive,
  best-effort selectors and flexible header/column resolvers. A portal redesign may
  require confirming a selector or column name on first run — each extractor logs a
  clear message and returns 0 rows rather than crashing.
- **Costa Rica (Registrelo) — public report API, browser-assisted:** `cr.py` was rebuilt
  16/08/2026. Registrelo is a React SPA behind `gateway.registrelo.go.cr`; its report
  catalogue is plain HTTP, but the **data** endpoint requires a reCAPTCHA v3 token, so the
  extractor opens an ordinary Chrome session on the portal and lets the page mint tokens as
  it does for any visitor (no stealth driver, no CAPTCHA service). Approvals come from a join:
  report 62 (`ProductAIMedicationPublic`, ~17k medicines) gives product→active-ingredient, is
  filtered in memory, and the matching products are resolved against report 12
  (`ReportsMS_Products_Public`) grouped by brand root to limit round-trips. That join is what
  finds brand-only names carrying no INN (`ADEMPAS`, `Efflusso®`). Submissions come from
  report 64 (`ProductsInProceduresPublic`), which has a server-side `activeIngredient` filter;
  it exposes no dates, so `submission_date` stays NULL. Registrelo publishes no concentration
  or dosage form, so those stay blank rather than being invented.
  ⚠️ **Prior data warning:** before this rebuild, `cr.py` looked for an Excel download button
  that does not exist, silently parsed whatever workbook was left in the shared download folder
  (Honduras'), and emitted 24 Honduran registrations tagged `country_code=CR`. Any consolidated
  file or report generated before 16/08/2026 should be treated as contaminated for Costa Rica.
- **Per-extractor download folders:** each extractor downloads into `output/_downloads/<key>/`,
  and `wait_for_download` only accepts files written *during* the call. Either guard alone
  prevents the cross-country contamination described above.
- **EMA — single XLSX feed:** EMA retired its per-report JSON endpoints (2026 redesign → 404).
  `ema.py` now downloads the one "Medicine" output spreadsheet
  (`medicines-output-medicines-report_en.xlsx`), keeps Human rows, matches on INN / active
  substance, and splits APPROVAL vs SUBMISSION by whether a marketing-authorisation / EC-decision
  date exists. It also threads `Therapeutic indication` + `Therapeutic area` + the `Biosimilar`
  flag as an `_indication_hint`, so the bevacizumab/ranibizumab post-filters now narrow EMA rows too.
- **Colombia approvals — substring match, paginated:** `co_approvals.py` filters Socrata with
  `upper(principioactivo) like '%TERM%'` (contains, NOT a leading anchor) so a registration where
  the INN is preceded by its salt (`TOSILATO DE SORAFENIB` → Nexavar), part of a combination
  (`METFORMINA + DAPAGLIFLOZINA` → Xigduo), or buried in a free-text formulation is still caught —
  matching a manual reviewer. Results are paginated (`$offset`) so a high-volume molecule is never
  silently truncated at the page size.
- **FDA — one row per product:** `fda.py` emits one canonical row per *product* (presentation), not
  one per application. A drugsfda application carries multiple products and each product multiple
  active ingredients; collapsing to `[0]` dropped sibling brands and mislabeled combos. `api` now
  lists every ingredient (`DAPAGLIFLOZIN + METFORMIN HYDROCHLORIDE`) and the PK is unique per
  presentation (`{app_no}-{product_number}` when >1 product).
- **Colombia submissions — DISABLED, out of scope (18/08/2026).** The Regulatory Affairs team
  tracks Colombian filings from an INVIMA transparency document they maintain themselves, which
  carries the recent movements this extractor never could: its Socrata source (`t2gj-yg8s`) is a
  historical archive ending 11/07/2024, so none of its 565 rows could ever fall inside the
  30-day alert window — they would only push stale data into the consolidated and collide with
  the team's own record. Colombia **approvals are unaffected and still run**.
  `co_submissions.py` and its tests stay intact; delete the `"disabled"` key on the
  `co_submissions` entry in `EXTRACTORS` to re-enable.
- **Ecuador (ARCSA) — two bulk downloads:** the portal's "Descargas" strip exposes four
  dumps; `ec.py` pulls the two the team tracks (`DEFAULT_REPORT_TYPES = [1, 2]`):
  - **`/reporte/1` — Registros Sanitarios Vigentes** → `APPROVAL` (~15k rows, ~44 MB).
  - **`/reporte/2` — Total de Solicitudes Ingresadas** → `SUBMISSION` (~2.9k rows). Keyed by
    `numero_solicitud`, dated by `Fecha_recepcion`, `status=PENDING`, and **no approval or
    expiry date** — nothing has been granted yet. Live: 91 matches, 26 inside a 30-day window.

  Report 1's `fecha_recepcion_solicitud` column is **not** an original filing date — across 161
  matched rows not one was earlier than that row's own approval date (40% equal it, 60% fall
  after it), so it tracks whatever later procedure touched the record. It is therefore **not
  written to `submission_date`**: approval rows leave that field empty and filings come only
  from report 2. The two never carry both dates, so a consumer can split approvals from filings
  on either `record_type` or the date field and get the same answer. Reports 3 (Caducados) and
  4 (Suspendidos/Cancelados) are described in `REPORTS` but not pulled; enable them per-run via
  `ec_report_types`.

  ARCSA exposes no per-molecule search: each report ignores any query term, so it is
  downloaded once and filtered in memory
  (like Honduras). It **runs by default in a full run** (adds ~25–45 s); skip it with
  `--no-ec`. **Tier-A never includes Ecuador** (the unattended preset stays fast).
- **Peru approvals:** launches Chrome on remote-debug port 9222 to clear Cloudflare
  Turnstile. Run **without** `--headless`; if a challenge appears, solve it and press
  Enter (unless `--non-interactive`).
- **Stable consolidated filename:** the master file is always `output/RPI_CONSOLIDATED.csv`,
  overwritten every run. It is uploaded to a SharePoint location that a Power Automate /
  Fabric dataflow reads from a fixed path, so a dated name would force a manual rename before
  every upload. A dated copy is archived under `output/_history/` so past runs stay auditable
  without putting a second consolidated file in front of whoever uploads.
- **Tracing novelty on rows that carry no date:** ~26% of the consolidated has neither an
  approval nor a submission date, almost all of it Costa Rica's filings (Registrelo publishes
  no date on that report). Three signals cover them, none of which invents a date:
  - **`extraction_date`** — first seen, so a filing that appears for the first time is dated
    by that appearance. Covers every row.
  - **The adminProcedures id inside `source_url`** — unique and monotonic (Spearman ρ = 0.948
    against the código), so it orders filings by recency even with no date at all.
  - **The `MS-YYYY-` prefix of the código** — carries the filing year for 271 of 566 CR rows
    (2024: 47, 2025: 104, 2026: 120).

  Costa Rica's filings are therefore keyed **per procedure**, `{código}-{procedureId}`: the
  código repeats (MS-2026-37103 comes back under two different procedures), and keying on it
  alone let `deduplicate` collapse them — dropping ~19% of CR filings and, worse, swallowing a
  genuinely new procedure that shared a código with a known one, so it would never surface as
  a novelty.
- **`extraction_date` means "first seen", not "last run":** re-extracting a record that has
  been in the file for months would otherwise re-date it as new. `_restore_first_seen()`
  carries the original date forward while every other field still refreshes, so the column
  can answer "which registrations are new to us" — useful as a safety net when a source is
  offline longer than the alert window (Colombia was down for exactly that reason on
  18/08/2026) and an approval issued during the outage would otherwise never be flagged.
- **Derived approval dates (Guatemala, Honduras):** neither registry publishes an approval
  date, so both are reconstructed from what they *do* publish, and each row carries a real
  date instead of a blank column:
  - **Guatemala** — a sanitary registration runs a fixed **five-year** term, so the issue
    date is `expiration_date − 5 years` (`gt._issue_from_expiry`). Day precision; 29/29 rows
    resolve. Leap-day expirations step back to the 28th.
  - **Honduras** — the registration number encodes month and year: `HN-M-MMYY-NNNN`
    (`hn.approval_date_from_registration`). Verified across all 72 HN-prefixed rows — the
    first pair spans 01–12, the second only 18–25, so it is **month/year, not month/day**.
    The day is therefore unknown and anchored to the 1st, which never overstates recency.
    The 30 legacy 5-digit registrations encode nothing and keep an empty date.
- **One molecule, one identity:** each portal is searched in its own vocabulary (LATAM
  registries use `DAPAGLIFLOZINA`, EMA/FDA use `DAPAGLIFLOZIN`, Peru/LATAM track turoctocog
  as `RFVIII`). `normalize.py` collapses every row's `molecule_search_term` onto the panel's
  canonical INN via `config.canonical_inn()`, so the molecule×country matrix shows one row
  per molecule instead of splitting a competitor's picture in two. Extractors keep tagging
  rows however their source spells things; an ad-hoc `--molecule` term passes through
  unchanged. Post-filters index the canonical INN as well as the source terms.
- **Colombia — source outage vs. real empty:** Socrata answers a query against an emptied
  dataset with `HTTP 200` + `[]`, which is indistinguishable from "this molecule has no
  registration". `co_approvals` therefore checks the dataset's total row count first: if the
  whole CUM publication is empty (as on 18/08/2026, when INVIMA republished all four CUM
  datasets with 0 rows), it reports **FAILED**, never EMPTY — so nobody can read it as "no
  competitor is registered in Colombia".
- **No outbound integrations:** the Notion/Airtable push and SMTP delivery were removed
  on 16/08/2026 — company compliance does not permit automated connectors. Nothing in this
  pipeline transmits data anywhere; it only writes files under `output/`.
- **Indication post-filters:** Tadalafil is narrowed to PAH/ophthalmic, Bevacizumab to
  ophthalmic, and Ranibizumab to biosimilars (config in `config.py → POST_FILTERS`). Since
  the canonical schema has no indication column, the decision uses product name, brand, and
  an `_indication_hint` threaded from indication-bearing sources (CO ATC description, SV
  indicaciones, HN grupo terapéutico, GT clase terapéutica). Dropped counts are logged per
  country (e.g. `Honduras post-filter dropped 47 row(s) [TADAFILO: 47]`).
- **Alias search:** LATAM extractors search each molecule's `latam_term` *and* its
  INN-variant aliases (`config.search_terms`), so a product registered under a different
  spelling is not lost — e.g. Tadalafil's LATAM term is `TADAFILO` but it is registered as
  `TADALAFILO`. Rows are tagged with the canonical `latam_term`; broad class aliases
  (`FACTOR VIII`) are excluded to avoid mislabeling.
- **Presence rows:** novel molecules flagged `track_if_absent` (Valoctocogene, Marstacimab,
  Efanesoctocog) that return no data in a successfully-searched country get a NULL-filled
  `record_type=NO_DATA` row (written to `RPIPRESENCE_canonical.csv`), so the report shows the
  molecule was checked. They are never counted as approvals/submissions. Toggle with
  `config.EMIT_PRESENCE_ROWS`.
